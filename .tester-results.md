  `asyncpg ... query = "-- Migration 2026-10-16 — worker_token hash-at-rest ... ALTER TABLE jobs DROP COLUMN IF EXISTS worker_token;"`.
- Reproduced in isolation (`-k backfills`, nothing else running) => NOT parallel-run/DB flakiness.

pg_stat_activity during the hang:

```
7770 | idle in transaction | Client:ClientRead | blocking_pids={} | SELECT t::text FROM jobs t WHERE user_id = $1
7772 | active              | Lock:relation    | blocking_pids={7770} | -- Migration ... ALTER TABLE jobs DROP COLUMN IF EXISTS worker_token;
```

Cause: the test keeps an app (SQLAlchemy) session in an open read transaction on `jobs`
(pg id 7770, ACCESS SHARE) while a second raw asyncpg connection (pg id 7772) executes the
migration DDL on the same table (needs ACCESS EXCLUSIVE). Self-inflicted wait, unbounded — no
`lock_timeout`/`statement_timeout`, so it blocks forever.

Fix belongs in the test (commit/close the app session, or set `lock_timeout` on the DDL
connection). NOT applied here — instructions: do not modify test or code.
